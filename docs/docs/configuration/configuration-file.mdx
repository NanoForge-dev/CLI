## Overview

Every NanoForge workspace, app or lib has a `nanoforge.config.ts` (or `.js`) at its root. It
exports its configuration wrapped in `defineConfig` from `@nanoforge-dev/config`. The CLI reads
this file to know how to build and start your game and, at a workspace root, to find the apps and
libs it contains.

Commands read the configuration of their `-d, --directory` folder (default: the current folder).
The CLI looks for `nanoforge.config.ts` first, then `nanoforge.config.js`, and fails with
`Configuration file not found` if neither exists. Every field except `type` is optional: a missing
field takes the default shown below.

## `type`

A config's `type` field discriminates between four shapes:

- `workspace` — a monorepo root listing its `packages`.
- `lib` — a shared library consumed by clients/servers.
- `client` — a browser-side NanoForge app.
- `server` — a server-side NanoForge app.

The config at the root directory the CLI is pointed at must be a `workspace` or a `client`/`server`
project — a bare `lib` config is not valid there. Inside a `workspace`, none of the packages it
resolves may themselves be of type `workspace`; nesting workspaces isn't supported.

## Defining a config

Wrap your config in `defineConfig` to get type-checking and editor autocompletion on its fields:

```ts
import { defineConfig } from "@nanoforge-dev/config";

export default defineConfig({
  type: "client",
  entryFile: "src/main.ts",
  libs: ["../../libs/my-lib"],
});
```

`defineConfig` is an identity function — it returns its argument unchanged.

## `workspace`

| Field      | Type                   | Default       | Description                                                                                                                                                                                                                            |
| ---------- | ---------------------- | ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages` | `string[]`             | `[]`          | <Tooltip tip="e.g. apps/*, apps/**/client, or a literal path like apps/client.">Glob patterns matched against directories relative to the workspace root</Tooltip>, each expected to hold its own `client`, `server`, or `lib` config. |
| `network`  | `"dedicated" \| "p2p"` | `"dedicated"` | Where the server app runs. `"p2p"` runs it in the browser of the first player who opens the game, the others joining that player over WebRTC: see [Peer-to-peer](#peer-to-peer).                                                       |

A directory matched by a pattern but missing a `nanoforge.config.ts`/`.js` is skipped without
error. A pattern that matches no project or lib at all only logs a warning, rather than failing
the whole resolution. A matched directory whose config is itself of type `workspace` throws.

### Example

```ts
import { defineConfig } from "@nanoforge-dev/config";

export default defineConfig({
  type: "workspace",
  packages: ["apps/*", "libs/*"],
});
```

### Peer-to-peer

With `network: "p2p"`, the same client and server apps run without a game server:

- `nf build` also builds each server app for the browser, into the client's output (`server/`).
- `nf start` sets `NANOFORGE_NETWORK_MODE=p2p` for both apps. The server process then only pairs
  players (WebRTC signaling) on its `LISTENING_TCP_PORT`, and the environment stays the same as
  with a dedicated server.
- A player who opens the game without `?room=` hosts it in their tab, and the game can show its
  invite link (`ctx.network.inviteLink`).

The [peer-to-peer networking page](/docs/engine/network/network-peer) explains the game side.

```ts
import { defineConfig } from "@nanoforge-dev/config";

export default defineConfig({
  type: "workspace",
  packages: ["apps/*"],
  network: "p2p",
});
```

## `lib`

| Field            | Type     | Default             | Description              |
| ---------------- | -------- | ------------------- | ------------------------ |
| `dir.assets`     | `string` | `assets`            | Where assets live.       |
| `dir.shared`     | `string` | `shared`            | Where shared code lives. |
| `dir.components` | `string` | `shared/components` | Used by the editor only. |
| `dir.systems`    | `string` | `shared/systems`    | Used by the editor only. |
| `dir.scenes`     | `string` | `shared/scenes`     | Used by the editor only. |

### Example

```ts
import { defineConfig } from "@nanoforge-dev/config";

export default defineConfig({ type: "lib" });
```

## `client` / `server`

`client` and `server` share these fields and defaults:

| Field              | Type           | Default          | Description                                                                                                |
| ------------------ | -------------- | ---------------- | ---------------------------------------------------------------------------------------------------------- |
| `entryFile`        | `string`       | `src/main.ts`    | Entry file that `nf build` bundles. Name it `main.ts`: the loaders run `main.js`.                          |
| `out.dir`          | `string`       | `dist`           | Build output folder. `nf build` empties it first; `nf start` serves it.                                    |
| `out.mainFile`     | `string`       | `main.js`        | Not used by `nf build` or `nf start` yet: the bundle is named after the entry file.                        |
| `dir.assets`       | `string`       | `assets`         | Its files are copied to the root of the build output. Subfolders are not supported yet.                    |
| `dir.packages`     | `string`       | `nf_modules`     | Folder for downloaded packages. No `nf` command reads it yet.                                              |
| `dir.components`   | `string`       | `src/components` | Where `nf create component` writes, and where the editor looks.                                            |
| `dir.systems`      | `string`       | `src/systems`    | Where `nf create system` writes, and where the editor looks.                                               |
| `dir.scenes`       | `string`       | `src/scenes`     | Used by the editor only.                                                                                   |
| `editor.entryFile` | `string`       | `src/main.ts`    | Entry file used with `nf build --editor` and `nf dev --editor`.                                            |
| `language`         | `"ts" \| "js"` | `ts`             | Language of the files that `nf create` generates.                                                          |
| `libs`             | `string[]`     | `[]`             | Relative paths to shared libs this app uses. `nf build` doesn't read it: it bundles what the code imports. |

A `client` also has:

| Field  | Type                                                                  | Default             | Description                                                                                               |
| ------ | --------------------------------------------------------------------- | ------------------- | --------------------------------------------------------------------------------------------------------- |
| `port` | `string`                                                              | `"3000"`            | Port of the web page that `nf start` serves. `nf start --port` overrides it.                              |
| `tls`  | `{ enable?: false }` or `{ enable: true, cert: string, key: string }` | `{ enable: false }` | Serve over HTTPS with this certificate and key. Use absolute paths. See [HTTPS](../commands/start#https). |

### Example

```ts
import { defineConfig } from "@nanoforge-dev/config";

export default defineConfig({
  type: "client",
  port: "8080",
  dir: { assets: "static" },
  libs: ["../../libs/shared"],
});
```

## Resolving defaults

Missing fields are filled in with the defaults for the config's `type`, deep-merging nested
objects like `dir` and `out`:

```ts
import { resolveConfig } from "@nanoforge-dev/config";

const resolved = resolveConfig({ type: "client", dir: { assets: "static" } });
// resolved.dir.assets === "static"
// resolved.dir.packages === "nf_modules" (default, not overridden)
```

Array fields (`packages`, `libs`) are replaced wholesale by an override rather than concatenated
with the defaults.

## Errors

- **`Configuration file not found at path: <folder>/nanoforge.config.ts.`** Neither
  `nanoforge.config.ts` nor `nanoforge.config.js` exists in the `-d` folder.
- **`Config file's default export is not a valid NanoforgeConfig`.** A field has the wrong type or
  `type` is not one of the four values. The lines below the message name the field.
- **`Config file has no default export`.** Add `export default defineConfig({ ... })`.
- **`Failed to load config file`.** The file throws or doesn't compile. The cause follows the
  message.
- **`Invalid config at '<folder>': the root config cannot be of type 'lib'.`** Run the command at
  the workspace root or in an app.
- **`Invalid config at '<folder>': a workspace package cannot itself be of type 'workspace'.`**
  Workspaces can't be nested.

In code, `@nanoforge-dev/config` throws a `ConfigParseError` whose `code` is `not-found`,
`load-failed`, `no-default-export` or `invalid-type`.
